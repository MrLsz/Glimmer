# 第一部分 Objective-C：消息发送的艺术

OC 的一切都围绕一句话展开：**方法调用不是「直接跳转到函数」，而是「给对象发一条消息」**。理解这句话，就理解了 OC 的类、isa、元类、缓存、转发全部机制。

## 一、对象与类的本质

### 1. 对象：isa + 一堆实例变量

一个 OC 对象在内存里只有两样东西：**一个 isa 指针，加上它的实例变量**。

```text
对象（堆上）
┌──────────┐
│   isa    │  ← 指向「类」，对象的全部能力都从这里来
├──────────┤
│  ivar1   │
│  ivar2   │
└──────────┘
```

关键认知：**对象本身不存任何方法**。方法存在「类」里，对象靠 isa 找到类，再找方法。

### 2. 类：也是一种对象

「类」在运行时是 `objc_class`，它**继承自 `objc_object`**——也就是说，类本身也是对象，也有 isa。这是 OC 对象模型最精巧的地方：

```text
objc_class
├── isa         ← 类的 isa 指向「元类」
├── superclass  ← 父类
├── cache       ← 方法缓存
└── bits        ← 指向类的数据（方法/属性/协议）
```

### 3. isa 链：实例 → 类 → 元类

- 实例对象的 isa → **类对象**（存实例方法）；
- 类对象的 isa → **元类**（存类方法）；
- 元类的 isa → 根元类，最终指向自己（闭环）。

```text
实例对象 ──isa──▶ 类对象(Person) ──isa──▶ 元类
                     │                        │
                     │ superclass             │ superclass
                     ▼                        ▼
                 类对象(NSObject) ──isa──▶ 根元类 ──isa──▶ 自己
```

**为什么类方法在元类**：因为类也是对象，调用 `[Person foo]` 和调用 `[p foo]` 走的是**同一套查找逻辑**——先从「类」里找，而类的「类」就是元类。一套机制，同时服务实例方法和类方法。

## 二、类数据的分层设计：ro / rw

这是 OC 类结构里最值得讲清楚的设计。

**问题**：类的方法列表，一部分是编译期就确定的（写死的代码），一部分是运行时可能新增的（Category、`class_addMethod`）。如果全放一起，要么浪费内存（每个类都要可写），要么破坏共享（运行时改动污染只读数据）。

**方案**：把类的数据拆成两层——

| 结构 | 全称 | 时机 | 存放段 | 作用 |
|------|------|------|--------|------|
| `class_ro_t` | read-only | 编译期生成 | `__TEXT`（只读） | 存编译期就确定的方法/ivar/属性 |
| `class_rw_t` | read-write | 运行时生成 | `__DATA`（可写） | 存运行时可增删的方法/属性/协议 |

```text
class_rw_t（可写）
├── ro ──────→ class_ro_t（只读，编译期数据，多进程共享可去重）
├── methods   ← 运行时动态添加的（Category 方法合并到这里）
└── ...
```

**设计意图**（这是重点）：
1. **省内存**：ro 放 `__TEXT` 段，只读、多进程共享、系统可去重——所有 App 里相同的系统类 ro 只有一份；
2. **支持动态性**：rw 按需分配，Category、运行时改类都作用在 rw 上，不动 ro。

> 一句话：**ro 负责「编译期写死的部分」，rw 负责「运行期可变的部分」**，二者通过指针连接，各司其职。

## 三、消息发送：一个方法怎么被找到

这是 OC 最核心的机制，也是性能优化的主战场。`[obj foo]` 编译成 `objc_msgSend(obj, @selector(foo))`，分「快速」和「慢速」两条路径。

### 1. 快速路径：方法缓存 cache

绝大多数方法调用只走这一步。每个类带一个 `cache`，是 `SEL → IMP` 的**哈希表**：

```text
cache 查找（O(1)）：
index = (SEL 哈希值) & mask       ← mask 是桶数-1（桶数恒为 2 的幂，用与运算代替取模）
bucket = buckets[index]
bucket.sel == sel ? 命中 : 线性探测下一个
```

**为什么快**：哈希 + 与运算，几条指令完成，命中即拿到函数指针直接跳转。

**写回机制**：方法第一次调用时走慢速查找，找到后**把结果写进 cache**，之后同样的调用直接命中缓存——这是「动态派发」还能保持高性能的根本原因。

### 2. 慢速路径：lookUpImpOrForward

cache 未命中时，走慢速查找：

```text
lookUpImpOrForward(cls, sel)：
  1. 遍历当前类的 method_list（已排序则二分，未排序则线性查后排序）
  2. 找到 → 写入 cache → 返回 IMP
  3. 没找到 → cls = cls->superclass，回到第 1 步（沿继承链向上）
  4. 直到 NSObject 还没有 → 进入消息转发
```

两个细节值得注意：
- **首次查找后排序**：方法列表线性查过一次后就排序，后续可二分，加速慢速路径；
- **继承链查找**：每级类都重复「查列表 → 查父类」，找到后同样写回**当前类**的 cache（不是祖先类），下次直接命中。

### 3. 找不到时：消息转发的三次机会

当整个继承链都找不到方法，OC 不会立即崩溃，而是给三次「补救」机会，一次比一次重：

```text
1. resolveInstanceMethod:      动态「造」一个方法补上（最轻）
2. forwardingTargetForSelector: 把消息「转手」给别人（较快）
3. forwardInvocation:           完整转发，可改参数、可多目标（最重、最慢）
   都未处理 → doesNotRecognizeSelector: → 崩溃
```

**三者的设计差别**（这才是重点，而不是记 API）：

| 机制 | 粒度 | 代价 | 典型用途 |
|------|------|------|---------|
| `resolveInstanceMethod` | 方法级 | 低 | 动态添加 `@dynamic` 属性的 getter/setter |
| `forwardingTargetForSelector` | 对象级 | 中 | 把消息转给组合对象（代理模式） |
| `forwardInvocation` | 调用级 | 高 | 完整拦截，可改参数、广播给多个对象 |

> 从「方法」到「对象」到「整个调用」，粒度逐步放大、代价逐步升高。选哪一步取决于你要控制的层级。

## 四、协议的底层：一份「方法清单」

协议在 OC 里**不绑定实现**，它只是一份「方法名 + 签名」的清单：

```text
protocol_t
├── name            ← 协议名
├── instanceMethods ← required 实例方法（只有 SEL + 类型编码，无 IMP）
├── optionalInstanceMethods
├── classMethods
└── protocols       ← 继承的协议
```

- 协议存 Mach-O 的 `__objc_protolist` section，运行时读取；
- `conformsToProtocol:` 沿「类的协议列表 + 父类链」查找；
- 协议方法只有**描述**（SEL + Type Encoding），没有 IMP——因为「谁遵守谁实现」。

## 五、Category 的底层：给类「追加」方法

Category 在运行时把方法**合并**进目标类，核心机制是 `attachCategories`：

```text
attachCategories 做的事：
把 Category 的方法 memmove 到【类方法列表的最前面】
→ 运行时查找时先命中 Category 方法 → 表现为「覆盖」原方法
```

**三个由此推出的结论**：

1. **Category 方法会覆盖原方法**（插在头部，优先命中）；
2. **多个 Category 同名方法，编译顺序靠后的生效**（后合并的插到更前面）；
3. **Category 不能加实例变量**——因为对象的 `instanceSize` 在编译期就定死了，运行时加 ivar 会破坏已分配对象的内存布局。要「加属性」只能用**关联对象**（全局哈希表挂载，不占对象布局）。

---

## 六、OC 的结构体：没有运行时

OC 的 `struct` 就是 C 结构体，**没有 isa、没有方法、没有继承**，就是一块连续内存。它和「类」是两套完全不同的东西：

| | OC 类 | OC struct |
|---|-------|-----------|
| 方法 | 消息发送 | 无（只能写函数） |
| 内存 | 堆 + 引用计数 | 栈 + 值拷贝 |
| 继承 | 有 | 无 |

> OC 里 struct 只用来做 `CGRect`、`CGPoint` 这类「轻量数据」，因为无运行时开销。真正面向对象的能力，OC 全押在「类」上——**OC 没有像 Swift 那样把 struct 也纳入类型体系**。

# 第二部分 Swift：类型与派发

如果说 OC 的核心是「消息发送」，那 Swift 的核心就是「**派发机制**」——类、结构体、协议三种类型，对应三种不同的内存形态和派发方式。这是理解 Swift 底层的关键框架。

## 七、三种类型，三种形态

| 类型 | 内存形态 | 派发 | 引用计数 |
|------|---------|------|:-------:|
| class（引用类型） | 堆：HeapObject | 动态（VTable） | 有 |
| struct（值类型） | 栈（非逃逸） | 静态（直接调用） | 无 |
| 协议类型 | 存在容器（可能堆分配） | 动态（见证表） | 看情况 |

### 1. class：HeapObject + VTable

Swift 类实例是 `HeapObject`，头部是**类型元数据指针**（相当于 isa）+ 内联引用计数：

```text
HeapObject
┌──────────────────┐
│ HeapMetadata*    │  ← 类型元数据（内含 VTable）
├──────────────────┤
│ RefCounts        │  ← 内联引用计数
├──────────────────┤
│ 属性...           │
└──────────────────┘
```

类的普通方法默认**动态派发**：子类 `override` 后，调用时查 VTable 定位到子类实现。`final`/`private`/`static` 修饰则退化为**静态派发**（直接调用，免查表）。

### 2. struct：栈上的值

结构体是值类型，默认在**栈**上，赋值/传参是值拷贝，无引用计数、无继承，方法**静态派发**（编译期确定地址，可内联）。这是 Swift 性能优于 OC 的关键来源之一。

### 3. 协议类型：存在容器 + 见证表（重点）

协议类型变量（`let s: Shape`）的问题在于：**编译器不知道具体类型有多大**，所以不能简单放栈上。Swift 用「存在容器」解决：

```text
存在容器（40 字节）
┌──────────────────────┐
│ inlineBuffer (24B)   │  ← 具体类型 ≤24B 直接内联；>24B 存堆指针
├──────────────────────┤
│ type (8B)            │  ← 具体类型的元数据
├──────────────────────┤
│ witnessTable (8B)    │  ← 见证表：协议方法 → 具体实现
└──────────────────────┘
```

**见证表（Witness Table）** 是协议派发的核心——它把「协议方法」映射到「具体类型的实现」：

```text
调用 s.area()（s 是协议类型）：
  1. 从存在容器取 witnessTable
  2. 查 area 槽位 → 拿到 Circle.area 的函数指针
  3. 调用
```

**一个关键限制**（面试高频）：带**关联类型**或 **Self** 约束的协议（如 `associatedtype Element`），编译器无法确定它的完整类型，**不能作为变量类型**，只能作泛型约束：

```swift
protocol Container { associatedtype Element }

// 错误：无法构建存在容器
// let c: Container = ...

// 正确：只能作泛型约束
func use<C: Container>(_ c: C) { ... }
```

## 八、方法派发的完整规则

Swift 的派发方式由「声明位置 + 修饰符」共同决定，这张表要能背下来：

| 声明方式 | 派发 |
|---------|------|
| struct / enum 方法 | 静态 |
| extension 方法 | 静态 |
| protocol extension 方法 | 静态 |
| class 普通方法 | 动态（VTable） |
| `final` / `private` / `static` | 静态 |
| `@objc` / `dynamic` | 消息派发 |
| NSObject 子类方法（默认） | 消息派发 |

三种派发的取舍：

| 派发 | 机制 | 性能 | 动态性 |
|------|------|------|:-----:|
| 静态派发 | 编译期定地址 | 最快（可内联） | 无 |
| 动态派发 | 查 VTable | 中 | 可 override |
| 消息派发 | objc_msgSend | 最慢 | 可 OC 调用 / KVO |

> **一句话选型**：要性能用 struct+泛型（静态），要多态用 class（VTable），要 OC 互操作/KVO 才用 `@objc dynamic`（消息）。派发方式的选择，本质是「性能 vs 动态性」的权衡。

## 附：高频速记

- **OC 对象 = isa + ivar**，方法在类里，靠 isa 找到类再找方法。
- **类也是对象**（继承 objc_object），类方法存在元类。
- **ro/rw 分层**：ro 存编译期数据（只读共享），rw 存运行时可变数据（支持 Category/动态添加）。
- **消息发送**：cache 哈希快查 → method_list 慢查（排序后二分）→ 三级转发。
- **消息转发三级**：方法级 resolve → 对象级 forwardingTarget → 调用级 forwardInvocation，粒度递增。
- **Category 方法头部插入**（覆盖原方法），不能加 ivar（关联对象代替）。
- **OC struct 无运行时**，只是连续内存。
- **Swift 三种形态**：class=HeapObject+VTable，struct=栈+静态派发，协议=存在容器+见证表。
- **带关联类型/Self 的协议不能作类型，只能作泛型约束**。
- **派发性能**：静态 > VTable 动态 > objc_msgSend 消息；选型是「性能 vs 动态性」权衡。
